# v1.3 master plan (required reading for every worker)

Date: 2026-09-22. Controller: Fable (assigns work only, doesn't write code). Executors: Opus (Kotlin core), Sonnet (docs / release), Grok (review).

## Goals

1. **Configurable endpoints**: the address, key, and model for the judge / reply / vision endpoints are all configurable, with presets and per-endpoint connectivity tests.
2. **Knowledge base + linked context**: users can maintain a local knowledge base (notes + contact profiles); every analysis automatically includes that contact's history and relevant knowledge, so replies stay consistent with the knowledge base; contacts link across apps via aliases.
3. **OCR capture**: apps whose control tree can't be read (Feishu message body, any unadapted app) fall back to screenshot + OCR; already-adapted apps fall back to OCR when the tree comes back empty.
4. Version 1.3, release build, README updated.

## Order and dependencies

A (API) → D (knowledge base / context) → B (OCR) → C (docs / release). One Opus agent per phase, in sequence; move to the next phase only once the build passes. **Only one agent touches code at a time** (gradle and files would conflict otherwise).

## Hard constraints (copied from CLAUDE.md, plus three more)

- Never auto-send, never touch money, keys never hit disk/logs/git, UTF-8, no `git commit`/`push`.
- **All user data (knowledge base, contacts, history) stays in the app's private directory only**, with a "clear" button provided; chat text never goes into logcat.
- **Old config must migrate automatically**: after upgrading, the original OpenRouter key, reply model, relationship description, allowlist, opacity, and toggles must all still work.
- Classic View + XML, no Compose; no Room (JSON files + in-memory cache is enough); ML Kit is only introduced in phase B.

## Shared contract (names are locked, reused across phases)

### New Prefs fields (built in phase A, read-only afterward)

```
// Judge endpoint (Jev)
judgeProvider: String   // "openrouter" | "typesafe" | "custom", default openrouter
judgeBaseUrl: String    // openrouter defaults to https://openrouter.ai/api ; typesafe defaults to https://api.typesafe.ai
judgeKey: String        // migration: old openRouterKey → judgeKey
judgeModel: String      // openrouter defaults to typesafe/jev-1.13 ; typesafe defaults to jev-latest
// Reply endpoint (any OpenAI-compatible chat completions)
replyBaseUrl: String    // default https://openrouter.ai/api/v1 ; fill in up to /v1, the client appends /chat/completions itself
replyKey: String        // blank = use judgeKey
replyModel: String      // reuses the old field, default deepseek/deepseek-chat-v3.1
// Vision endpoint (for OCR, OpenAI-compatible, supports image_url)
visionBaseUrl: String   // defaults to the same as replyBaseUrl
visionKey: String       // blank = use replyKey → judgeKey
visionModel: String     // default qwen/qwen2.5-vl-72b-instruct (available on OpenRouter in most regions; user can change it)
// Context (phase D)
contextEnabled: Boolean       // record and inject history, default true
contextHistoryCount: Int      // how many recent history messages to inject, default 30
autoSummary: Boolean          // auto-summarize contacts, default true
// OCR (phase B)
ocrEngine: String             // "mlkit" | "vision", default mlkit
ocrForUnknownApps: Boolean    // unadapted apps use generic OCR, default true
ocrFallback: Boolean          // OCR fallback when an adapted app's tree comes back empty, default true
ocrAutoAnalyze: Boolean       // auto-analyze in OCR mode, default false (manual tap)
```

Judge endpoint request path: openrouter → `{judgeBaseUrl}/alpha/decisions`; typesafe → `{judgeBaseUrl}/v1/systemone`; custom → the user enters the full URL into `judgeBaseUrl`, posted as-is. The request body is the same `{model, state, questions}` for all three.

### Model client split (phase A)

```
jev/JudgeClient.kt   // Jev only: judge(snapshot, context) / rank(candidates)
jev/ReplyClient.kt   // generation only: draft(snapshot, context) → 3 candidates; summarize(text) → summary (used by D)
jev/VisionClient.kt  // vision only: extractDialog(bitmap) / ocrLines(bitmap) (used by B; phase A only builds the shell)
jev/HttpJson.kt      // shared POST JSON + backoff + error classification (extracted from the postJson currently in JevClient)
```
The old `JevClient` is deleted or turned into a thin facade; callers (ChatCaptureService, SettingsActivity's connectivity test) switch to the new classes. Error messages must include "which endpoint + HTTP status code + first 120 chars of the response."

### Knowledge base / context data model (phase D)

Storage: `context.filesDir/kb/notes.json`, `kb/contacts.json`, `kb/logs/<contactId>.json`.

```
Note(id, title, content, tags: List<String>, alwaysOn: Boolean, enabled: Boolean, updatedAt)
Contact(id, name, aliases: List<String>, apps: List<String>, relationship: String, notes: String,
        autoSummary: String, summaryAtCount: Int, updatedAt)
LogEntry(side, text, ts, app)          // one file per contact, capped at 300 entries, appended with (side,text) dedup
ChatContext(contact: Contact?, history: List<LogEntry>, notes: List<Note>, budgetChars = 1500)
```

Matching rule: chat title == contact.name or ∈ aliases (case-insensitive, trimmed) → matched; if unmatched and contextEnabled → auto-create a Contact from the title (apps records the source package). Note retrieval: alwaysOn notes are always included; the rest are scored by bigram overlap between the note's "title + tags + content" and the chat's "title + last 6 messages," taking the top 5, within the total character budget.

Injection: Jev's `state` gets a `background` field (relationship + contact notes + auto-summary + matched notes) and `history` (past messages); the reply prompt adds "here is the background and knowledge base about me and the other person — replies must stay consistent with it, and must not invent facts the knowledge base doesn't contain."

### OCR layering (phase B)

```
capture/ocr/ScreenCapture.kt   // wraps AccessibilityService.takeScreenshot: rate-limit ≥1s, an enum of failure reasons, Bitmap callback
capture/ocr/OcrEngine.kt       // interface: recognize(bitmap, region): List<OcrLine(text, bounds)>
capture/ocr/MlKitOcr.kt        // com.google.mlkit:text-recognition-chinese (bundled)
capture/ocr/VisionOcr.kt       // goes through VisionClient, can return structured dialog
capture/ocr/BubbleGrouper.kt   // OCR lines → bubbles: grouped by line spacing and left/right alignment; side decided by which edge the bubble sits against
capture/GenericOcrAdapter.kt   // any package: crops out the top bar (if it has a title) and the input area (if it has an EditText), OCRs the middle region
capture/FeishuAdapter.kt rework // reads bubble_content_container rectangles + read-status container from the tree to decide "me"; OCRs each rectangle's text
```
Accessibility config adds `android:canTakeScreenshot="true"`. On screenshot failure (FLAG_SECURE, interval too short, system restriction), show a human-readable message in the overlay.

## Acceptance criteria (each phase: build passes + install + controller verifies on real device)

- A: each of the three endpoint cards' connectivity tests pass on the settings page; switching the reply endpoint to DeepSeek official and back, WeChat / QQ analysis still works; the old key still works after upgrade with no re-entry needed.
- D: create 1 note in settings (containing a made-up fact) + set relationship and aliases for a contact; when analyzing that contact, reply candidates reflect that fact; the log shows "Knowledge N / History M"; the clear button works.
- B: Feishu conversation body is read via OCR and analyzed; pick any unadapted app (e.g. DingTalk / Telegram / Weibo DMs) and get candidates via generic OCR; OCR fallback still works when WeChat's disguise is turned off.
- C: README platform table updated, version 1.3, release build signature verified.

# Revision (2026-09-22 00:30, after Grok 4.7 review; supersedes the above where they conflict)

## Phase A additions
- Migration happens exactly once: after writing the `prefs_migrated_v13=true` flag, stop reading `openrouter_key`; if the user clears `judgeKey`, it must not come back. Not a single old storage key name changes.
- `replyKey` / `visionKey` staying blank means "inherit"; when saving, **don't** replace a blank relationship description with a default value.
- A preset button must atomically write both the base URL and the model name together; the vision endpoint, when not separately configured, is pinned to the OpenRouter vision model — **it does not follow the reply endpoint.**
- Vision requests: images use `data:image/jpeg;base64,` (`Base64.NO_WRAP`); for Tongyi compatible-mode, the image part goes before the text part; DeepSeek official doesn't support image_url — the connectivity test should say "this endpoint doesn't support vision."
- Compatibility of the new `background` field in Jev's state: hit the live API with one fixture first to confirm whether `alpha/decisions` ignores it or returns 400; add a line to the question instructions in English: "facts in background are given context, not off-topic" — same for the ranking question.

## Phase D (knowledge base / context) narrowed
- **Off-disk by default**: `contextEnabled` defaults to false; the settings toggle reads "Record chat history (stored locally only, used for linked context)," with the home-screen readiness card suggesting it can be turned on. README updated to match.
- **No auto-creation, no auto-summary**: contacts are only created manually by the user (or via "save current chat as contact" in the overlay menu); `autoSummary` is deferred, and `ReplyClient.summarize` is left unwired.
- **Retrieval is only two tiers**: alwaysOn notes are always included in full (counted against the budget separately, never truncated); other notes are included only if their tag/title is a substring of the chat title or last 6 messages, capped at 5 matches; no bigram scoring.
- Name normalization: strip leading/trailing whitespace and zero-width characters, strip a trailing `(number)` group-size suffix, then match name / aliases case-insensitively.
- History dedup: only drop a duplicate when (side, text) exactly matches a message already on screen and the text is at least 4 characters long.
- Storage: JSON files with a single writer (`synchronized` + atomic write to a temp file, then rename); "clear" only deletes `filesDir/kb`, leaving keys and the allowlist untouched.
- The overlay shows a line reading "Knowledge N · History M."

## Phase B (OCR) narrowed
- **1.3 only does two things**: ① Feishu: use the `bubble_content_container` rectangle plus the read-status container from the tree to decide "me," running ML Kit OCR on each rectangle (stripping "Read" out of the OCR result); ② a generic entry point: "Read screen once (OCR)" in the overlay menu, manually taking one full-screen OCR pass on any app and analyzing it — **not automatic, and not split into me/other by left/right (everything is recorded as "other" and flagged "unsplit" in the panel)**. Vision-model OCR does not enter the main capture path.
- Adapter contract split: `extract` returning `null` means "not in a chat window"; returning `ChatSnapshot(messages empty)` means "in a chat window but the tree has no message text." The service only runs the OCR fallback for the latter case, with failure backoff (1s → 2s → 4s, capped at 30s) — never firing every second.
- Screenshot implementation: prefer API 34's `takeScreenshotOfWindow`, fall back to `takeScreenshot(DEFAULT_DISPLAY)`; hide the overlay before capturing and restore it after; in the callback, `copy(ARGB_8888)` then immediately `close()` the HardwareBuffer; rectangles are re-read in the callback and scaled by the bitmap/screen ratio; global rate limit ≥ 1000ms; a human-readable message for each of error codes 1/2/3/4/6.
- Adding `canTakeScreenshot="true"` to the accessibility XML **requires disabling and re-enabling accessibility to take effect** (write this into acceptance). The disguised-class-name service may be specifically denied screenshot access on HyperOS — the first step of phase B is to fire a real-device `takeScreenshot` and check the errorCode; if refused, stand up a separate, non-disguised, screenshot-only service.
- ML Kit: pin to `com.google.mlkit:text-recognition-chinese` (bundled, not the play-services variant), `ndk.abiFilters = arm64-v8a`, pick a version that supports 16KB page alignment; record the size increase and "recognized once on this GMS-less phone" in acceptance.
- The phone won't be around tonight, so phase B's real-device verification is deferred to the morning; the code can be written first.
